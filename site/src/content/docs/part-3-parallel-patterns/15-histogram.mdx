A histogram counts how many input values fall into each bin. On a CPU it is
one line in a loop, `hist[data[i]]++`. On a GPU each thread takes some of the
elements, and that one line becomes the hard part: two threads with the same
value both want to add 1 to the same counter.

In 2015 Nikolay Sakharnykh timed two GPU histograms of 1080p images, one that
updates counters in global memory and one that counts into a copy per block in
shared memory first. On a Maxwell GPU (GeForce GTX TITAN X) the shared memory
version was "almost 2x faster". On the Kepler GPU he tried (GeForce GTX TITAN),
the global version won on most inputs. The input mattered too: he calls an
image where every pixel has the same value "the worst case scenario for
atomics since all threads are trying to write to the same address." This
chapter explains all three effects.

## Why `hist[b]++` is wrong in parallel

`hist[b]++` is three steps: read `hist[b]`, add 1, write it back. If two
threads read the counter before either writes, both write the same new value
and one count is lost. Chapter 22 steps through this race; here it is enough
that it happens, and that the result can still look plausible.

An **atomic** operation does the three steps as one. The CUDA C++ Programming
Guide says `atomicAdd()` "reads a word at some address in global or shared
memory, adds a number to it, and writes the result back to the same address",
and that "these three operations are performed in one atomic transaction". No
other thread can touch the word in between, so no count is lost:

```cpp
atomicAdd(&hist[data[i]], 1u);
```

Two details from the same section matter for histograms:

- Plain `atomicAdd` is atomic at device scope, so it is correct across all
  blocks of the grid. `atomicAdd_block` is atomic only within a block, and
  `atomicAdd_system` also covers the CPU and other GPUs.
- These atomics have relaxed memory ordering. They count correctly, but they
  do not order other memory accesses. That is all a histogram needs.

## Contention

Atomicity has a cost when threads collide. The Programming Guide, in its
description of the SIMT architecture, says that when an atomic instruction of
a warp writes the same location from several threads, "each read/modify/write
to that location occurs and they are all serialized, but the order in which
they occur is undefined."

So the time a histogram takes depends on the data, not only on its size.
Spread values over many bins and the atomics go to different addresses.
Put every value in one bin and every thread queues on one counter. This is
**contention**: the cost is set by the busiest bin.

Integer addition gives the same total in any order, so an integer histogram is
exact whatever order the queue runs in. A `float` sum built with `atomicAdd`
can differ in its last bits from run to run, because floating point addition
is not associative.

## Privatization

The fix is to give each block its own copy of the histogram, a **private**
histogram in shared memory:

1. The block zeroes its copy and calls `__syncthreads()`.
2. Each thread adds its elements to the block's copy with shared memory
   atomics. Only the threads of this block compete for these counters.
3. After another `__syncthreads()`, the block adds each nonzero bin of its copy
   to the global histogram with one global atomic.

The number of threads that can collide on one counter drops from every thread
in the grid to the threads of one block. The global histogram now gets at most
one atomic per bin per block, instead of one per element. The price is the
merge, and a shared memory copy per block, `BINS * 4` bytes: 1 KB for 256
bins.

This is also why Kepler and Maxwell disagreed. Sakharnykh's article explains
that Kepler emulates shared memory atomics in software, while its global
atomics benefit from conflict resolution in the L2 cache; Maxwell has hardware
support for shared memory atomics. A private copy only pays off when updating
it is cheap.

## The simulation

The simulation is a small launch: {THREADS} threads count {N} values into
{BINS} bins with a grid-stride loop, so each step is one round in which every
thread issues one atomic. Atomics on the same address wait in line; atomics on
different addresses run at the same time. A step costs as many **slots** as its
longest queue. The top panel runs the global kernel, the middle one the
private copies, and the bars add up the slots of each kernel.

Things to try:

  Each private copy sees only its block's 8 threads, and the merge adds one
  atomic per block: {slots('hot', 4, 'shared')} slots.
- **One hot bin, 1 block.** With a single block the private copy is just a
  second global histogram: {slots('hot', 1, 'shared')} slots, one more than the
  global kernel. Privatization needs many copies to help.
- **Uniform, 4 and 8 blocks.** The values are already spread, so the global
  kernel's queues are short: {slots('uniform', 4, 'global')} slots. Four blocks
  give {slots('uniform', 4, 'shared')}, but eight give
  {slots('uniform', 8, 'shared')}: with every bin nonzero in every block, the
  merge queues 8 blocks on each bin.

them with NVRTC on a machine without `nvcc`. `cuda/histogram.cu` includes it,
times each kernel on three inputs and checks it against a CPU count. Every
version is tested against `np.bincount`, exactly, for uniform, skewed and
one-bin inputs.

## Measure it yourself

On a GPU, from `kernels/ch15-histogram`:

```sh
make -C cuda run
python numba/histogram.py
python triton/histogram.py
ncu --section MemoryWorkloadAnalysis_Tables ./cuda/histogram
```

Each program prints, for each input and kernel, the time of one histogram and
its throughput in bytes read per second. Things to look for:

- How much slower the global kernel is on the one-bin input than on the
  uniform one. That gap is contention.
- Whether the shared kernel is faster than the global one, on which inputs,
  and how much its time changes between inputs.
- How your GPU's ratios compare with the model's slot counts. The model gives a
  shared atomic and a global atomic the same cost, and real hardware does not.

## Exercises

**1. Predict the slots.** For the one hot bin input with {THREADS} threads in
`B` blocks, each running {ROUNDS} rounds, write the model's slot count for the
shared kernel as a formula in `B`. Which of 1, 2, 4, 8, 16 and 32 blocks gives
the fewest slots?

<details>
<summary>Answer</summary>

Each round, one block's `32 / B` threads queue on the hot bin of its copy, so
the four rounds take `4 x 32 / B = 128 / B` slots. In the merge, all `B` blocks
queue on that bin of the global histogram: `B` slots. The total is
`128 / B + B`: 129, 66, 36, 24, 24 and 36. Eight or sixteen blocks are best, at
24, near the square root of 128. Fewer blocks leave long queues in the copies,
and more blocks make the merge queue long. The simulation stops at 8 blocks;
it shows {slots('hot', 8, 'shared')}.

</details>

**2. More copies, more slots.** On the uniform input, why does the shared kernel
take {slots('uniform', 8, 'shared')} slots with 8 blocks but only
{slots('uniform', 4, 'shared')} with 4?

<details>
<summary>Answer</summary>

With 8 blocks of 4 threads, each round's queues in a copy are short, but by the
end almost every bin is nonzero in every block. The merge then sends
{merges('uniform', 8)} global atomics, and up to 8 of them queue on one bin.
With 4 blocks the merge sends {merges('uniform', 4)}. Step to the merge in the
simulation and compare the queue heights. On a real GPU each block counts many
more elements than here, so the merge is a small part of the work, but the same
trade applies: every copy adds one merge per bin.

</details>

**3. Fix the bug.** Someone deletes the second `__syncthreads()` in
`hist_shared`, the one before the merge, and the result is right in their test.
What can go wrong?

<details>
<summary>Answer</summary>

A thread can reach the merge loop while other threads of its block are still
adding to the private copy. It reads `local[b]`, adds that to the global
histogram, and the later additions to `local[b]` are never merged: counts go
missing. Whether it happens depends on how the warps are scheduled, so a test
can pass by luck. Deleting the first barrier is also a bug: a thread could add
to a bin that another thread has not zeroed yet. `compute-sanitizer --tool
racecheck` reports both.

</details>

**4. Why skip zeros?** The merge does `if (local[b] > 0) atomicAdd(...)`. On
the skewed input with 4 blocks, how many global atomics does the model's merge
send, and how many would it send without the check?

<details>
<summary>Answer</summary>

With the check, {merges('skewed', 4)}: one for each block and bin with a
nonzero count. Without it, every block adds every bin, {4 * BINS}. On the real
kernel's 256 bins, a skewed input leaves most bins at zero in every block, so
the check saves most of the merge.

</details>
