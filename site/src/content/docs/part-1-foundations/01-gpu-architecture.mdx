number is correct, but a CUDA core is not a core in the CPU sense. None of them

write in the rest of the course.

## From the chip to a core

A GPU chip is built from four layers, from the outside in:

1. **Memory.** Gigabytes of DRAM sit next to the GPU die, not on it. Everything
   your kernel reads from a pointer starts here. CUDA calls it global memory.
2. **The L2 cache.** One cache on the die, shared by everything else on it. All
   traffic to and from DRAM goes through the L2.
3. **Streaming multiprocessors (SMs).** The units that compute. The A100 and
   H100 have over a hundred of them and the T4 has 40, all identical, all
   working independently.
4. **Partitions.** Each SM is split into four partitions. A partition has its
   own warp scheduler, its own slice of the register file, and its own
   execution units, including the FP32 units that NVIDIA counts as CUDA cores.

So a CUDA core is one arithmetic lane inside a partition. The thing that
actually runs instructions is the warp scheduler, which drives many lanes at
once. That is the subject of chapter 4.

## Many threads, waiting cheaply

A CPU core makes one thread fast. It has large caches to keep data close,
branch predictors to guess what comes next, and out-of-order logic to find work
while it waits. A GPU spends that silicon on more arithmetic units instead, and
accepts that each thread is slow.

The trick that makes this work is in the partition. A load from DRAM takes
far longer to return than an arithmetic instruction takes to run. Rather than
wait, the warp scheduler issues the next instruction of a different warp that
is ready. Switching costs nothing, because every resident warp keeps its own
registers in the register file the whole time. Nothing is saved or restored.

This is why the register file is so large: {a100.registerFileKbPerSm} KB per SM
on all three GPUs below, enough for 65,536 32-bit registers. It holds the state
of every thread the SM is juggling at once. It is also why a GPU needs far more
threads than it has cores. With only one warp per partition, little could hide
the wait.

<Aside type="note">
  A thread on a GPU is not slower because its arithmetic is slow. It is slower
  because it shares its partition with many other threads and only gets an
  instruction issued when it is ready and picked. The total work done per
  second is what is fast.
</Aside>

## The memory hierarchy

The last zoom level in the simulation adds up each kind of storage across the
whole chip. Small and fast storage is spread over the SMs; large and slow
storage sits in one place.

| Level | Where it is | Who can see it |
|---|---|---|
| Registers | In each partition | One thread |
| L1 cache and shared memory | One block of memory per SM | The threads of one block share the shared memory part |
| L2 cache | One per chip | Every SM |
| DRAM (global memory) | Next to the die | Every SM, and the CPU through copies |

One result surprises most people. Added over all SMs, the registers are not
small. On the {t4.name} they hold {formatKb(totals(t4).registerFileKb)}, more
than its {t4.l2Mb} MB L2 cache. Switch the simulation to the T4 and go to the
last step to see it.

## How this connects to your code

Chapter 2 introduced blocks of threads. Here is where they go:

- A block runs on one SM and does not move while it runs. Its threads can use
  that SM's shared memory and wait for each other. By default, threads in
  different blocks cannot, because their blocks may be on different SMs. The
  H100 relaxes this with thread block clusters, which later chapters cover.
- An SM can hold several blocks at once, as long as it has a free block slot
  and enough registers, shared memory and warp slots for all of them.
  Chapter 5 works out how many.
- More SMs means more blocks running at the same time. A launch with fewer
  blocks than the GPU has SMs leaves SMs idle.

## Look at your own GPU

On a machine with an NVIDIA GPU, `nvidia-smi` prints the model, driver and
memory. From Python, PyTorch reports the numbers this chapter uses:

```python
import torch

p = torch.cuda.get_device_properties(0)
print(p.name, f"compute capability {p.major}.{p.minor}")
print("SMs:", p.multi_processor_count)
print("L2 cache:", p.L2_cache_size // 2**20, "MB")
print("Memory:", p.total_memory // 2**30, "GB")
```

Both work inside the course Docker image.

## Exercises

**1. Count the lanes.** An H100 SXM5 has 132 SMs with 128 FP32 cores each.
How many FP32 cores does it have? Check your answer in the simulation.

<details>
<summary>Answer</summary>

132 * 128 = 16,896.

</details>

**2. Registers per thread.** An A100 SM has 65,536 32-bit registers and can
hold at most 2,048 threads (64 warps of 32). If every one of those threads is
resident, how many registers can each thread use?

<details>
<summary>Answer</summary>

65,536 / 2,048 = 32 registers per thread. A kernel that needs more registers
per thread fits fewer threads on each SM. Chapter 5 turns this into the
occupancy calculation.

</details>

**3. Fill the GPU.** You launch a kernel with 64 blocks on an A100. At most how
many of its 108 SMs can be busy?

<details>
<summary>Answer</summary>

64. A block never splits across SMs, so at least 44 SMs have nothing to do.
This is one reason to launch many more blocks than there are SMs.

</details>
